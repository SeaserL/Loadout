## 语义与限制

- `/api/usage/quota` 是响应头/冷却/队列压力观察；`quotaTotal=null` 时原生可能显示 `percentRemaining=100`，不是实际剩余额度。
- `/api/usage/provider-limits` 只读原生 Provider 缓存，保留 `source/fetchedAt`；没有数据或数据陈旧必须按未知处理，不能当零或保证余额仍有效。本轮未开全量配额刷新。
- `/api/usage/budget` 是按 API key 的本地预算；`keys/:id/usage-limits` 是日/周使用限额。两者原生窗口、超限边界和订阅例外不同。沿用原生逻辑，不伪装成统一余额。
- 预算依据已记录成本，非并发预占款；单次和在途请求可能超过限额。未知价格的使用限额路径会阻止后续调用；成本估算与真实账单仍需区分。
- `/api/providers/:id/models?refresh=true` 通过选定账号凭证发现并可持久化目录；`sync-models` 手动更新原生每账号缓存。不是纯离线读。Provider 聚合目录不代表每个账号都能调用其中模型。
- 原生自动修剪 Combo 陈旧步骤、自动写 Codex/Claude profile 均默认关闭，保持默认；未开启全局后台同步。

## 首轮发现与测试修正

- 测试最初把 key 修改写成 PUT，原生实际为 PATCH；修正测试及随包操作文档。HTTP 层两类限额都拒绝负数；零值表示不限制该窗口。不得以零值表达禁止调用。
- 命名账号在已有适配中是优先账号；测试改为同时验证默认 failover 仍限于允许账号，以及 allow_account_failover=false 严格固定时拒绝越权账号。没有修改该行为。
- Combo 预算错误不保证包含单模型错误码 budget_exceeded；通过 HTTP 429、预算原因和上游计数未增加判断，不为测试改写错误格式。
- 原生账本有60秒批量持久化周期，但预算计算包含内存待写条目；本轮最终专项设置预算后5ms读回已超限，随后请求在上游前被拦截。不能把批量持久化间隔直接描述成必然的60秒执行延迟。
- 首个057封包仅修正README后重新封装，运行时代码未变。最终包 identity 单独记录，旧包及测试错误历史保留小型证据，临时包验收后删除。


## 维护成本与结论

本轮上游仅改变既有 `src/proxy.ts` 的3处白名单文本；自有工具仅改变CLI查询白名单与精确056→057升级对。没有新增上游业务文件、依赖、schema、定时器或路由实现。累计上游tracked运行时仍20文件、+160/-22；不包含自有模块、外围工具和构建配置，不能当作整个fork维护量。

这两项适合继续直接复用原生实现，无需扩大融合补丁。配额先开放只读观察/缓存；真实Provider余额刷新和实际账号可用性未验，不能宣称已支持所有原生Provider。费用预算也不是严格预付费扣款。继续保持不做UI、不切正式环境、不提交上传；商汤风控、CommandCode401、WorkBuddy自然轮换仍DEFERRED。
