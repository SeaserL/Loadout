# OmniRoute 原生 SQLite 路线隔离验证（042）

日期：2026-10-30。最终发布目录验收132/132通过；这不构成正式迁移批准。

**结论：值得继续以OmniRoute为主底座融合，接受原生SQLite；不需要为RouteSnapshot重构热路径，也不应退回全量自研。** 当前适配能保持小范围，但不是零成本升级插件。下一阶段应固定基线、补真实使用入口的受控验收与迁移工具；本轮仍不进入UI或正式部署。

## 本轮问题与边界

用户明确优先少维护，接受OmniRoute原生SQLite，不要求复制RouteSnapshot、零SQL、Rust内部类型、原命令或UI。只保留凭证安全与个人账号规则；不做UI、不改正式安装/数据/凭证，不调用真实Provider。

实现只在两个新工作树中：v3.8.51 `c1e30b7676975feb298b49eff6ff58923c04b89e`，v3.8.52 `ad6f33f66bda34eba98645d3bfdabbde294bc843`。使用官方backend-only构建、完整instrumentation与独立standalone目录，携带Node 24.19.0、keytar原生绑定。未增加第二套Router，没有改schema或migration。

## 功能归属与实际适配

| 功能块 | 保留谁的实现 | 自有变化 |
|---|---|---|
| SQLite、schema、数据迁移、账号健康与租约 | OmniRoute | 接受原生同步查询/写锁行为，不建RouteSnapshot或SQL memo |
| 协议翻译、流式、取消、执行、failover | OmniRoute | 三个协议在共同入口编译账号限制；实验开启时阻止上游响应前的兼容保活帧影响failover边界 |
| 主池/子池、优先级、轮转、账号生命周期 | OmniRoute | 子集使用固定连接ID；显式空集停用key，避免原生空数组被理解为主池；点名首选/strict与授权范围求交 |
| Provider凭证 | Windows Credential Manager +窄adapter | SQLite只存ref；修改/删除/失败写入清理；缺失ref明确失败；启动清理孤立条目 |
| 客户端key | OmniRoute管理与hash验证 | 禁止可逆保存及reveal；v51实验关闭有陈旧撤销行为的鉴权cache TTL，v52使用自身撤销实现 |
| 导出/恢复 | 原生数据库备份 +自有加密vault | 阻止原生JSON导出/导入旁路；独立登录与CSRF保护的vault端点，scrypt+AES-256-GCM；恢复需匹配数据库与vault |
| UI、可视化、免费资源目录 | 本轮未做 | Magpie仍是后续视图参考，不进入推理链 |

账号别名在每个请求从原生连接表读取，不保存第二份账号状态。自有policy只约束上游选择；原生状态仍是事实来源。

凭证变更由一个串行写入边界包住原生CRUD。删除实际删除系统凭证，不暗藏历史秘密。数据库回滚不等于凭证回滚：必须恢复匹配的加密vault，缺失时拒绝发出上游请求。OS store与SQLite不是原子事务；本轮验证SQL写失败清理与启动清理一个中断窗口，不声称覆盖任意崩溃指令点。

## 实跑暴露的问题及修正

1. 第一轮58项、57通过。恢复只有ref的数据库而缺少系统凭证时，原实现返回null，仍发出没有有效鉴权的请求；宽松mock接受它，形成真实反例。改为明确抛出缺失引用错误，验收条件收紧为零上游请求。
2. 第二轮132项、129通过。v51轮换或删除client key后，旧key仍可请求；独立小诊断确认是撤销行为问题，不是状态码断言过严。仅在v51实验将相关鉴权cache TTL置零，继续使用原生SQLite验证。v52本身的实测撤销有效，不复制旧版补丁。
3. v52修改上游key时SQL已提交，但返回值解密把新明文误当成ref，报500。修正写后返回接缝，先转换成ref再走读取；不放宽缺失ref拒绝条件。两版验收分别使用不同的新凭证。
4. metadata白名单曾误拦原生apiKeyHealth写入；现在接受并校验有限的状态/计数/时间字段及selectedKeyId，不允许任意对象混入。最终验收另外检查健康持久化错误日志数量。
5. 原先所有账号状态更新都会遍历OS凭证库，第二轮单请求约350ms。改为依据当前DB引用与已加载/暂存ref，仅在出现无引用条目时执行OS清理。失败暂存、删除、启动恢复随后通过验收；这不改变SQLite，也不新增路由缓存。**该调整没有显著改善350ms间隔，不能把原延迟主要归因于OS清理。** 后续对照确认主要是原生请求队列的主动间隔。

失败与诊断记录保留在实验`runs/`及脱敏`evidence/`，没有把最终通过覆盖成“从未失败”。

## 验收解释与剩余边界

- 三种实际客户端HTTP协议为Chat Completions、Responses、Messages；验证返回结构、流式工具参数拼接、取消关闭上游、输出后不再重放。底层Provider是loopback mock，不是三个真实客户端或真实供应商E2E。
- 覆盖点名首选、strict、同模型切换、授权子集、空池、主池、新增账号、改名、停用/启用、串行/并发轮转。stateful Responses明确400，未实现原生会话固定；它仍是实际客户端迁移前需要明确取舍的能力。
- 只验收审计过的API key profile。OAuth刷新、网页cookie、复杂metadata、所有免费平台及MCP/CLI等其他管理旁路未验收；未知认证和metadata被拒绝。带凭证的URL、异常上游回显等需要在扩大Provider范围前专项审核，不能据本轮哨兵扫描宣称整个上游产品都安全。
- “凭证不落盘”指应用普通数据库、日志、普通备份不保存可恢复秘密；Windows受保护凭证库和用户主动生成的口令加密vault是明确例外。Node字符串无Rust drop清零保证，未证明内存转储/分页文件无秘密，也未做独立密码学审计。
- 原生账号模型名可含斜杠，与旧`provider/account/model`兼容语法存在歧义。本轮模型名无该歧义；后续可以换成原生连接选择界面/参数，不能为保旧命令再做大层兼容。
- 单实例后台是本轮边界；没有验证两个进程共享同一SQLite及vault的缓存一致性。升级必须停旧包后启新包，不双写同一凭证空间。
- 沿用原生WAL与`synchronous=NORMAL`（`src/lib/db/core.ts:1272`）；没有做真实断电、磁盘满或数据库损坏测试。成功备份恢复不等于异常断电耐久性已经证明。
- 构建复用已有依赖；本轮重新运行的是完整standalone目录，不是再次ZIP压缩解包。只记录入口hash，不冒充完整包树hash。构建跳过全量类型检查；62项上游focused测试与融合包验收分别记录。
- `--v52-only`中间诊断曾在已停服务后执行最后一个删除检查，得到fetch failed；已修复测试分支。正式结论使用独立的完整两版本132项链；v52撤销另有HTTP诊断，不能把该诊断脚本错误称为产品删除缺陷。
- 1/5/10并发只是本机小样本，p95在10样本时接近最大值；没有无适配原生包的严格性能对照，不把差值归因于SQLite或声称精确适配开销。

## 后续采用边界

本轮最终复验通过，建议固定v3.8.52作为后续开发底座，把约束profile和底座无关验收随发布保存。每次上游升级先按固定tag移植有限接入点、跑凭证/账号/协议/备份恢复矩阵，再决定是否采用；不自动追随每个发布。

正式迁移前仍需：收窄并审计生产管理入口，移除测试控制端点，固化安全启动配置，验证真实使用的Provider和客户端，处理stateful需求，完成受控旧数据迁移与回滚。无需先做Magpie UI，也没有理由恢复完整自研网关。

实验源码、包和脚手架按用户要求保留。040遗留SWC缓存自动删除曾被审批拒绝，本轮复用其中一个，没有绕过拒绝，也不宣称已清理。
