# 053 订阅行为移植与原生别名、账号池迁移

本轮按用户指定顺序接回已有Codex订阅行为，再接OmniRoute原生迁移能力。只运行隔离mock，不登录真实账号、不启动真实客户端、不改正式安装/数据/凭据，无提交上传。使用前轮脱敏路由元数据，没有重新读取正式数据库。

## 实现与来源

| 功能 | 本轮结果 | 复用来源与边界 |
|---|---|---|
| 登录状态、额度扫描 | 显式命令查询app-server，必要时回退session记录 | 按`crates/providers/src/codex.rs`行为移植到`fusion/subscription-scan.mjs`；只返回元数据，不导入官方CLI token，不在推理请求中启动CLI。测试用模拟app-server。 |
| Loadout自己的受控登录 | device-code、内存pending、逐账号双确认、默认关闭转发 | 按`crates/providers/src/codex_subscription.rs`和`crates/core/src/oauth.rs`已有行为移植；没有带入Rust Core。 |
| 订阅凭证生命周期 | 合并刷新、失效后停重试/禁用、删除、加密备份恢复 | 复用已有OS vault适配和OmniRoute原生账号字段；SQLite只存引用，id_token丢弃，通用管理接口不能绕过托管凭证规则。 |
| 三协议与工具 | Responses上游经原生执行器处理，Chat/Responses/Messages入口与工具内容验证 | 只移植旧订阅请求规范化与流式要求；工具参数不另写转换器。 |
| 旧别名、池、受限客户端 | 精确别名映射、成员顺序、账号交集、严格点名及8RPM | 直接调用原生model-combo-mappings、combos、keys与权限PATCH；不新增Router/schema。 |

受控登录凭证使用独立`credentialProfile`标记。原生apiKey/refreshToken列保存vault引用只是存储接线，不代表把官方客户端token作为普通API key导入。含此类账号的迁移使用“受控登录绑定→map”的两步流程；一次性API-key导入会明确拒绝。

实际旧池的脱敏结构（GPT三成员、WorkBuddy、商汤12账号×5模型、受限客户端）均进入迁移计划。清单保留21个源账号及未绑定/只读状态；不能由几条池的mock成功推断21个真实账号全部可迁。`loadout/default`等虚拟别名必须显式给出目标，测试输入不是替用户决定正式默认模型。自动虚拟路由仍排除订阅账号，明确的GPT池可以选择它。

本轮只迁入Codex相关扫描与受控登录；其他订阅扫描器、常驻全Provider扫描调度未一并迁入。

## 发现的问题及最小修复

- 托管凭证元数据初次被旧白名单拒绝：仅增加明确列出的订阅字段，未开放任意metadata。诊断包不作为交付证据，最终后台从源码重编。
- 原生创建key接口忽略rateLimits：迁移工具在创建后调用原生权限PATCH，未修改上游限流器。保留早期第9次仍返回200的失败记录。
- 升级mock将GET空body按JSON解析：修正模拟服务器，清理中断实例后重跑，未修改产品协议层。
- 第一轮集中回归停机备份ENOENT，后续恢复与测速连带失败：补充确定性反例，证明锁文件在检查后删除会使status/assertStopped/takeLock抛出ENOENT。自有工具仅将锁文件消失作为正常状态，活跃锁与损坏锁继续拒绝；重封工具后再验最终ZIP。原结果见首次集中回归。
- 早期新增GPT failover断言曾一次失败；补充实际attempt记录，后续源码包复验通过。保留专项历史，不以删除失败记录表示修复。

## 维护范围与边界

相对固定上游，运行时接入点19个文件、+133/-21；前轮为17个、+128/-19。新增接入点只有default executor和chatCore，其他变动落在既有适配接入点。**这个diff不包含自有适配文件和外围工具，不能当作全部维护量**。本轮新增4个自有后台模块共231物理行（约14.8KB），另有扫描/迁移工具及测试。具体清单见改动规模。

原生SQLite、schema migration、combo、协议转换继续保留。新后台完整构建成功，最终仅工具修正通过重封包纳入；构建仍沿用backend-only及跳过全量类型检查的既有流程，不能宣称全仓类型检查通过。Rust未修改或重编。许可证检查348包、0违规，7个缺少bundled license文件的既有提示保留；无新第三方代码来源。

真实OAuth成功率、外部账号可用性未由mock证明；商汤风控、CommandCode401、WorkBuddy自然凭证轮换继续DEFERRED，不扩展客户端排障。

## 结论与下一步

这条路线仍比恢复全量自研更符合“少维护”：已把已有订阅行为接回，同时把别名、池和权限交还原生能力。真实全量迁移仍要求有效账号绑定及明确默认别名，不能自动切换正式环境。

下一步按[功能清单](../architecture/fusion-backend-status.md)接原生只读模型目录、用量/延迟/成本和路由诊断；再接免费目录/Radar的更新时间与同步。逐项开放和验证，不新建统计库或第二套路由，也不开始UI。
