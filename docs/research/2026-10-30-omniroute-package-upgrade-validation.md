# OmniRoute 融合包、跨版本升级与 SQLite 热路径验证

日期：2026-10-30。ExecPlan 040；承接039，不涉及UI开发或正式环境。

> 后续前提更新（041，同日）：用户明确要求以少维护为目标重新评估原生SQLite。本页保留原始测试和条件性结论；其“停止融合”建议不适用于放开RouteSnapshot要求后的路线。新推荐为[OmniRoute原生SQLite与最小适配](2026-10-30-omniroute-native-sqlite-assessment.md)，不是退回全量自研。

## 结论

**在继续保留现有 Loadout 热路径和安全约束、并以“少维护”为优先目标的前提下，不建议继续推进三项目深度融合。保留正式 Loadout，停止进入融合UI及正式迁移阶段。**

这不是“OmniRoute构建不出来”或“SQLite太慢”的结论。两版带适配的完整后台已经构建成功，真实包到包的数据升级和回滚也可运行。安全与账号接缝的代码量仍小；未成立的是“这些接缝足以承接全部既有契约，且以后只需维护几个插件”的假设。

现阶段最明确的分界是：保留SQLite作为持久化层完全合理；为了几毫秒查询耗时全面改写路由没有依据。但若保留Loadout选路前只读内存的规则，以及不让数据库写锁牵连请求的隔离目标，就必须改变上游的状态读取、租约清理和持久化边界。请求内缓存与单点写入去重均没有解决该问题。这将超出凭证与账号策略薄适配。

可以继续参考OmniRoute的协议实现、Magpie的可视化设计；本报告不建议继续把三套产品实现拼成一个私人长期fork，也不把“保留正式版”解释为重新批准扩张Loadout全量自研功能。

## 完整后台与升级结果

第一份v52包暴露了源码宿主看不出的错误：Webpack改写动态`createRequire`后，OS凭证初始化失败，后台报`SECRET_STORE_UNAVAILABLE`并拒绝服务；没有降级为明文存储。改为Node内建module API明确加载打包内keytar后重新构建。v51的静态external导入可用。最终适配均只加载发布目录内的原生模块。

初次6GB堆上限构建OOM；8GB完成。过程中补齐了隔离依赖安装时省略的Windows原生/optional包。依赖缺失、共享node_modules导致的external解析差异，以及一次测试构建重入，是本次验证工具链的问题，不作为“上游不能正常构建”的证据。最终未修改上游构建配置文件。上游构建默认跳过TypeScript错误，不能把build成功当作全仓类型检查通过。

## 一次实际升级需要维护多少补丁

冻结补丁在`development/experiments/omniroute-phase2/evidence/v51.patch`和`v52.patch`；统计和前向应用错误在`patch-upgrade.json`。以下按LF归一化并经上游Prettier格式化后的可审查补丁统计；格式整理发生在验收包构建后，没有改变逻辑。探针与生产方向的adapter分开计数。

| 项目 | v51 | v52 |
|---|---:|---:|
| 修改上游原文件 | 8 | 8 |
| 原文件增加/删除行，含探针接缝及格式整理 | +69 / -16 | +40 / -9 |
| 自有安全、policy、启动模块 | 198行 | 201行 |
| 实验probe与管理控制端点 | 196行 | 258行 |
| 为旧版补齐的上游MIT字段映射模块 | 181行 | 0，已原生提供 |

新版8处原文件接缝包含测试探针挂点；生产方向的三个自有模块合计201行。格式化前压缩写法只有144行，不能拿压缩代码行数美化维护量。**不能说补丁已经膨胀到需要重写上游；代码规模本身仍小。**

但旧版完整补丁直接前向套到新版时，有**6个原文件不能直接应用，另有1个新增文件已被上游原生提供**。初始未补齐旧版嵌套凭证保护的简化补丁只有4处失败；不能拿该较小数字代表最终等价安全补丁。

## SQLite：耗时、锁影响与重构边界

探针按请求AsyncLocalStorage区分选路前、选路/发送前与发送后；以Undici真实请求创建事件标记首次dispatch。只记录SQL模板、调用点和耗时，不记录绑定值、正文或凭证。

早期只计prepared statement时约191次、1.6ms；后来加入原生`exec`，发现热路径还反复执行`CREATE TABLE IF NOT EXISTS model_capabilities`，完整数字增加。不能把这两种计数混用，也不能把未计入的事务等待当成不存在。

最终源码诊断每组40请求（合成模型、本机mock、上游节流行为保留）：

| 模式 | 发送前已观测SQL调用均值，含exec | 探针计时均值 | HTTP p50 / p95 |
|---|---:|---:|---:|
| 原适配 | 247.68 | 3.20ms | 347.67 / 363.01ms |
| 请求内SELECT memo | 136.60 | 2.04ms | 349.21 / 363.35ms |

这里的exec探针计时包含调用栈记录开销，应视为实际SQL时间的偏高估计；prepared statement计时在采集调用栈前结束。底层原生事务内部语句不全部经prepare/exec包装，立即事务另行计时，不能声称表格穷尽每一条物理SQL。

完整后台包另跑30请求/组：首轮目录运行原适配p50约352.55ms，memo约352.92ms，无SQL探针约349.65ms。最终ZIP解包复验对应p50为349.75/350.96/352.03ms，p95为359.44/369.10/370.51ms。约350ms的总延迟包含上游队列/节流及框架处理，不能归因于SQLite；mock结果也不是公网Provider性能承诺。memo减少重复读取，未带来可辨识的端到端收益。

更关键的受控反例是另一个进程在**测试DB**持有500ms写锁：

1. 原路径：请求约105→606ms，选路前`domain_circuit_breakers`持久化等待约535ms。
2. 只去重未变化熔断器写入：请求仍约166→630ms。第二次归因证明`exclusiveConnectionLeases.reconcileExpiredExclusiveConnectionLeases()`经`getExclusiveLeaseOccupancy()`在选账号时启动立即写事务，等待约538ms，尽管测试没有使用独占租约。

探针中的熔断器去重只是因果实验，未作为正式修复：跨进程修改、重启恢复、异常处理及状态版本一致性尚未覆盖。除两处已证实阻塞外，还观察到租约UPDATE、压缩组合默认行INSERT，以及多个模型/权限/代理配置读入口。

由此区分三个问题：

- **是否要放弃SQLite？不需要。** 当前查询耗时不支持这种结论。
- **是否必须重写整个Router才能改善延迟？没有证据支持。** 有价值的第一步是避免每次请求同步写入未变化状态，并把过期清理移出关键路径；这两处应争取上游修复。
- **能否靠上述小优化满足现有RouteSnapshot边界？不能。** 请求内memo仍执行约137次SQL；租约、key权限、模型能力和代理配置涉及失效与一致性，不可用全局缓存一包了之。要保持当前“选路前只读内存/原子状态”规则，需要更广的状态边界改造，并经过新的设计与验证。

## 未被本轮证明的事项

没有真实Provider流量或额度消耗；不推断OAuth刷新、所有管理API、所有协议入口、跨进程凭证撤销、内存清零、长期运行、用户环境自动升级器或所有Provider目录迁移都已验收。账号别名映射在启动及实验控制更新后刷新，尚未完整接入所有原生管理变更事件。不能把聊天协议的通过扩张成Responses/Gemini/Anthropic入口全部遵守同一约束。发布包本轮没有补跑SSE首字节、并发吞吐和长时间压力测试；039/源码诊断中已有的相关证据不冒充本轮发布包验收。

Node字符串不能自动提供Rust secret类型的内存清零保证。跨版本数据升级成功也不表示既有Loadout数据库可以直接导入OmniRoute；本次迁移的是两个融合试验版本的OmniRoute测试DB。

## 决策依据

若仅评估“OS凭证ref + 账号约束 + 可重启后台能否接上”，答案是能，而且补丁规模可控。这是本轮积极结果。

但当前项目规则没有授权放宽热路径边界与凭证保证。继续正式替换需要的工作已包含状态生命周期改造、多协议一致性、管理变更同步和完整安全路径审计，不能据201行adapter宣布只剩接UI。结合“优先少维护”，本轮建议**停止按当前边界推进深度融合，保留隔离验证资产和稳定生产版**。这个判断不依赖构建期间的工具脚本错误，也不把SQL调用次数当成性能失败。

ADR-019保持提案状态；本报告没有修改正式ADR-004或热路径约束。若以后选择直接接受OmniRoute原生的同步SQLite模型，那属于明确变更产品契约后的另一条路线，需要单独决策，不能通过本轮实验自动获得授权。
