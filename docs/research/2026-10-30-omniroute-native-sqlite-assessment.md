# OmniRoute原生SQLite路线：以少维护为目标重新评估

日期：2026-10-30。ExecPlan 041。仅评估；没有新增运行测试、生产变更或UI开发。

## 结论与前提修正

**这条路线比保留Loadout原有内部架构的深度融合更合适，应成为后续首选验证方向。接受OmniRoute原生SQLite、状态管理、协议执行链和管理方式，集中维护凭证保护与确实缺失的账号语义；不退回全量自研。**

040的运行证据仍然有效，但其停止建议依赖“选路前必须只读RouteSnapshot、维持原有内存/延迟契约”的前提。用户现在要求以少维护重新评价技术选择，该停止建议不能直接沿用。SQLite进入热路径不等于凭证会进入SQLite，也不意味着账号范围必然失效；这几个问题需要分别验收。

当前建议是**值得继续完成最小安全适配的验证**，并非已具备正式迁移条件。两版实验包已经成功升级，说明无需先重写Router才能运行；仍有明确的安全生命周期和协议覆盖缺口。既有稳定Loadout仅作为迁移前服务和回滚保障，不是默认继续扩张的产品底座。Magpie视图降为以后可选的设计参考，不作为此次路线成立的条件。

## 保留结果保证，放开实现方式

| 范围 | 本路线的处理 |
|---|---|
| SQLite、schema、migration、内建缓存/租约/熔断器 | 接受上游实现；不复制一套RouteSnapshot，不维护第二个Router |
| Rust/Tauri、Named Pipe、旧CLI、旧URL/模型名语法 | 不要求复刻；允许用上游API、key范围及配置档承接同一使用需求 |
| 性能目标 | 不以“SQL次数为0”或旧版微秒/毫秒预算作否决条件；看实际并发、流式停顿、超时和适配增量 |
| 凭证 | Provider秘密由OS保护存储，应用DB仅引用；client key只持久化hash；日志/错误/普通备份和导出不带可恢复秘密；失败不降级明文 |
| 账号规则 | 主集合/显式子集、空集拒绝、顺序或每请求轮转、首选与strict区别、同模型failover、禁止范围逃逸；有状态会话不能被轮转破坏 |
| 其余现有安全配置 | 继续使用本地监听、管理/推理鉴权和默认不记录正文；不另造安全框架，也不因放开SQLite而主动开启泄露功能 |

这里将用户所说“凭证不落盘”沿用为**应用普通持久化不保存可恢复凭证，OS受保护的凭证存储除外**。Windows Credential Manager本身也会持久化加密数据；若解释为任何物理介质都不能出现任何凭证字节，便与重启恢复凭证的现有使用方式不一致。

Node内存中的字符串不具备Rust secret对象同等的drop清零承诺，进程转储、分页以及同用户恶意程序也不由这个adapter解决。接受这一不同的威胁边界，需要在后续正式采用ADR中明确，不能把它写成“绝对不落盘/绝对不留存”。本轮未变更正式ADR-004。

## 接受原生SQLite后的实际风险

### 1. 锁等待会影响响应，但没有证据证明个人使用不能接受

040实测：mock请求发送前的SQL探针计时均值约3.20ms，请求内memo后约2.04ms，未出现可辨识的端到端收益。注入500ms写锁时，请求约105→606ms；仅去重熔断器持久化后，租约清理仍等待约538ms。这证明存在锁影响，**没有测出日常使用中500ms锁的发生频率，也没有证明长期重构比接受偶发等待更划算**。

固定v3.8.52的`src/lib/db/core.ts:1261–1273`已使用同步驱动、WAL、`busy_timeout=2000`及`synchronous=NORMAL`。源码明确说明争锁会阻塞Node事件循环。单次busy处理可等待约2秒；多次SQL与重试叠加时，不能把2秒当作整个请求上限。同一事件循环中的其他请求、健康检查和流式转发也可能延迟，这是源码机制推断，040没有完成并发流式影响实测。

WAL允许读写并行，但仍同时只有一个写入者；busy timeout是等待后失败机制，不能消除锁。见[SQLite WAL并发说明](https://sqlite.org/wal.html#concurrency)与[busy timeout定义](https://sqlite.org/c3ref/busy_timeout.html)。

低维护应对：本地磁盘、单后台实例、不让外部工具同时写同一DB；备份/升级安排短暂维护窗口。先以实际常用客户端负载验收原生行为。若只是少量非关键重复写，优先上游改进；不预先建设异步数据库层或全局快照。减少写入者也不能保证没有事件循环停顿或慢磁盘影响。

### 2. 异常断电可能丢失最近已确认的状态写入

WAL加NORMAL以耐久性换取同步开销，电源故障/硬重启后，最近提交可能回退；不能把它简单等同于“SQLite容易损坏”，也不能误认为每次普通应用崩溃都会丢数据。见[SQLite WAL性能与耐久性权衡](https://sqlite.org/wal.html#performance_considerations)。

对个人网关，丢少量用量统计、冷却状态通常是可接受候选；刚修改的账号授权若回退，后果更重要。上线前应验证配置恢复和启动后的有效范围，重要策略修改保留无秘密配置备份。不要为了此项重写持久化引擎；若有不可回退的授权需求，再针对配置事务评估同步级别，而非先假定全量重构。

### 3. 数据库升级仍有操作成本，已有可行的低成本处理

040实际v3.8.51→v3.8.52升级应用16项migration，原账号ID/ref、client key及规则可用，旧包+升级前数据副本回滚通过。它没有证明旧程序可直接安全打开新schema，也没有证明所有未来版本均兼容。

采用固定版本、停服务备份、升级验收、失败恢复旧包和旧数据即可延续这条已验证路径，不自建完整更新系统，不同时运行旧新后台写同一个DB。普通DB备份含账号与用量等metadata，即使没有密钥也不能视为公开资料。

**判断：以上SQLite风险属于需要验证的运行取舍，不再是架构不匹配导致的自动否决理由。**

## 剩余主要成本：凭证与账号适配

| 问题 | 本轮证据与实际后果 | 最小处理方向 |
|---|---|---|
| 普通导出可以重新带出秘密 | 源码`src/app/api/settings/export-json/route.ts`调用解密视图并序列化Provider连接，提供JSON附件。这是有管理鉴权的功能，不是已证明的未授权漏洞；但OS引用适配不会自动关闭它。040未执行该导出用例 | 默认拒绝含秘密导出，或仅输出metadata；不要先重写加密备份产品。client key reveal不能返回原文，应改为重置流程 |
| 新Provider/刷新路径新增秘密字段 | `providerSpecificDataSecrets.ts`集中维护已声明字段，未知字段保持原样；原生储存函数并非只处理API key。旧测试不能证明未来新增字段安全 | 先覆盖实际需要的认证类型；升级时检查字段表、OAuth刷新及写入入口。未审计类型明确不可用，不自动宣称所有免费平台均已安全支持 |
| OS store与DB不是一个原子事务 | 当前adapter先写OS store、再写ref；数据库写失败可能留下孤立凭证。删除/换key/恢复旧DB后的清理与引用寿命未完整接入；过早删除旧ref也会破坏回滚 | 集中处理写入失败、撤销、删除和恢复；保护回滚期仍需的ref，不简单“删除账号即删所有key”。OS store不可用明确失败，不能读不到便扩大路由范围 |
| 凭证内存缓存长期存活 | 实验adapter预热并保留凭证字符串，启动后的外部撤销及同步尚未完整覆盖；原生绑定打包在040曾实际失败 | 单后台所有写入经统一入口，撤销同步更新缓存；原生绑定/Node升级做启动与读写回归。并非恢复Rust内存生命周期 |
| 空集合在上游表示不限制 | `src/sse/services/auth.ts:1133–1135`只对非空allowedConnections过滤；现有adapter以拒绝哨兵适配空集 | 优先用原生禁用入口/明确deny配置承接（需验证），必要时保留小型约束编译。不能把Loadout空子集原样写成`[]` |
| 管理变更、多个协议和并发可能绕过既有小样本 | 040通过Chat串行scope/轮转/strict/同模型failover；当前alias缓存只在启动与实验seed刷新，未覆盖全部管理入口、Responses及Messages | 接受原生ID/配置形式，尽量删除自有alias镜像；确需首选账号差异才补小钩子。逐项验实际消费者，不要求实现另一套协议转换 |

上述凭证问题多数在换成内存Router后仍然存在；不应归咎于SQLite。拒绝凭证泄露和账号越权仍是必要产品保证，但实现保证的方法可以变化。

## 怎样控制私人维护量

建议保留一套上游运行时，增量只承担两个职责：

1. **凭证边界**：OS store引用、client hash-only、秘密读写/撤销/导出保护。接入现有持久化与管理边界，不复制协议执行器。
2. **账号语义差异**：优先上游配置实现子集/顺序/轮转，仅补空集、首选/固定与范围交集等确实缺失的行为。旧命令、旧寻址字符串可换，语义不能偷偷取消。

SQLite查询/租约/熔断器、协议转换、Provider接入、普通统计和管理界面由上游维护。删除实验probe、实验管理端点和为保持内存热路径而设的memo/dedup；SSE不能重复发送/偷偷重放、stateful账号固定属于实际请求正确性，应验上游能力或采用其受支持配置，不能因名为“实现细节”而丢掉。

040的201行与8处接缝是**原实验版**的规模，包含部分试验挂点；6处旧补丁前向失败既有机械漂移也有模块拆分。它们说明有维护成本，但不足以推出“必然比自研贵”。新路线可以删除一部分兼容代码，凭证生命周期补齐也会增加代码；本轮没有制作新补丁，**不虚报缩到多少行、多少冲突或多少工时**。

接受上游数据模型，还能避免维护SQL表与自有快照之间的全量同步机制。剩余自有凭证缓存仍需要正确生命周期，不能把这一收益扩大为“没有缓存一致性问题”。升级验收围绕这两个职责固定下来，比要求整个上游执行Loadout内部架构更可控。

## 下一阶段只补这些验收

建议在新授权的隔离阶段做以下有限验证；本轮没有启动它们：

- **凭证闭环**：真实管理API创建/改key/删除/导入/普通导出/重启；注入OS store失败和DB锁/写入失败，扫描DB/WAL、临时文件、日志与导出。标准API key先通过；需要的OAuth另验刷新，不以一个Provider代表所有认证方式。
- **账号闭环**：从原生管理入口改范围/新增或删除账号/恢复配置，确认下一次获准请求的实际候选；空集拒绝、禁止池外与跨模型逃逸，串行轮转保持a,b,c,a；并发检查公平性及范围，不要求响应完成顺序也严格a,b,c。
- **实际使用的协议**：Chat以及确实使用的Responses/Messages；首字节之后不重复重放、取消释放上游、有状态会话保持账号或明确拒绝。不先补齐用户不用的全部Provider和协议。
- **运行风险**：同机原生配置与适配配置比较，按1/5/10并发作为候选负载、持续流式输出与管理写入并行；注入0.5/2/5秒锁，观察健康检查、取消、错误和锁释放后恢复。以上是建议测试点，不是已确认的用户负载或生产SLA；不再使用“零SQL”作门槛。
- **升级成本**：拆掉探针/旧兼容需求后重做一次同样的两标签升级，分类记录必要安全改动与机械重定位；普通失败采用旧包+旧数据恢复，并检验凭证ref仍有效。

若这些测试能在集中适配内通过，应继续基于OmniRoute；若必须复制Router、协议转换或大量Provider模块才能守住凭证/账号边界，再判定此底座不合适。那时也应比较其他成熟底座或缩小支持范围，而不是自动回到全量自研。
