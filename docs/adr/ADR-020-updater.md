# ADR-020: 1.0 Software Updates

- **Status**: Accepted
- **Date**: 2026-11-03
- **1.1 revision (2026-11-06, ExecPlan 071)**: 见文末“1.1：两个版本和 AI 组件包”。

## Context

1.0 没有更新器，0.4 的更新器（ADR-018）也装不了 1.0。用户要求给 1.0 做一个。

1.0 和 0.4 的差别决定了不能照搬：

- 包是一个 2 万多文件、约 380 MiB 的文件夹，不是三个 exe，只能整个换。
- 运行时是 Node，正在运行的 `node.exe` 和 `Loadout.exe` 都在要被替换的文件夹里。
- 后端进程带 `isolation-guard`，它拦截 OmniRoute 自带的更新检查，这条规则不应该放开。
- README 承诺过“空闲时不连接任何上游”。

## Decision

**一个独立的短进程做更新**：`tools/updater.mjs`，由控制面按需启动，做完就退出。它不加载 `isolation-guard`，自己只允许连接 `github.com` 和 GitHub 的资产 CDN，并且只用 HTTPS。后端和 OmniRoute 的出站规则不变。访问过的主机同样写进 `egress.log`。

**不用 GitHub API。** `github.com/.../releases/latest` 会跳转到最新的正式 Release，从地址里就能读到版本号，草稿和预发布不会是 latest。API 的匿名配额按 IP 算，每小时 60 次，共享出口上很容易被别的程序用光，开发机上就真实遇到了 403。

**检查只在窗口打开时发生。** 没有后台定时任务：控制台读更新状态时，如果距离上次检查超过 6 小时，才启动一次检查。失败的检查同样算一次，断网时不会反复尝试。窗口关着、只有网关在跑时不产生任何出站。可以在设置页关掉。`loopback-only` 模式下不检查。

**下载和安装都要用户点。** 检查是自动的，380 MiB 的下载和会中断请求的重启不是。不做自动安装。只保留一个待安装的版本，下载更新的版本时旧的会被删掉。安装不需要联网，连不上 GitHub 时已校验的下载仍然可以装。

**更新说明走专用的 `update.open_notes`。** 地址由后端按版本号拼出，不接受调用方传入，`system.open_url` 仍然只开登录页。

**信任边界和 ADR-018 相同**：固定仓库、HTTPS、SHA-256。SHA-256 不是独立签名，能发布 Release 的人就能发布更新。为此：

- 只接受比当前高的三段版本号（不降级）、固定名字的资产和固定的下载地址，体积有上限。每一跳重定向都先检查主机。
- 解压时拒绝路径穿越、链接、ZIP64、未知压缩方式和重复路径。
- 解压后按包内 `fusion-manifest.json` 逐文件核对哈希，多一个少一个都拒绝，`productVersion` 必须等于要装的版本。

**换文件夹由当前版本的脚本完成**，不执行下载包里的脚本。`apply-update.ps1` 先复制到包外再运行，因为它要换掉自己所在的文件夹：

1. 把新版本解压在同一个磁盘上，下载和校验都在这一步，期间网关照常工作。
2. 停掉这个实例的后台和窗口（只按路径匹配这个包里的进程），备份数据库。
3. 重命名旧文件夹，再把新文件夹改名到原路径。快捷方式因此不用变。
4. 用新版本启动后台并确认就绪。
5. 成功后才删除旧文件夹和备份；原来开着窗口就重新打开。失败就换回旧文件夹、恢复数据库、启动旧版本，并记下原因。

**只在同一个 OmniRoute 版本之间自动更新。** `Instance` 本来就拒绝打开不同上游版本的数据，换上游要走 `upgrade` 命令。校验时发现上游版本变了，就提示按 Release 说明手动升级，不动现有安装。

**发布约定**：资产名 `Loadout-<版本>-portable-windows-x64.zip`，配同名 `.sha256`，内容格式 `<哈希>  <文件名>`。

**系统代理**：后台的环境变量是清理过的，更新进程读 Windows 的系统代理设置并用于这次下载。否则在需要代理才能访问 GitHub 的网络里更新永远失败。

## Alternatives

- **放进后端（Next 进程）做**：要放开 `isolation-guard`，OmniRoute 自带的更新检查也会跟着通过。下载和解压还会占用网关进程。
- **Tauri 的 updater 插件**：面向单个安装包，还要求单独的签名体系，放不下这种文件夹式的便携包。
- **增量更新**：省流量，但每个版本要多维护一套差分。一年也发不了几次，整包替换够用。
- **下载包里自带安装脚本**：等于在验证完成前就信任新版本的代码，ADR-018 已经排除。
- **Ed25519 签名**：能在 GitHub 账号被盗时多一层保护，但要管理私钥和发布流程。安装需要用户点击，先保持和 ADR-018 相同的边界，以后需要再加。

## Consequences

每次更新下载约 380 MiB，期间多占约 2 GiB 磁盘（压缩包、解压后的新版本、旧版本）。

1.0.0 没有更新器，已经下载 1.0.0 的用户要手动换一次。

重启时进行中的请求会中断，安装按钮前有确认。

数据库备份只在安装过程中保留，新版本确认就绪后删除。如果新版本启动成功、之后才发现问题，只能手动装回旧版本。

## 1.1：两个版本和 AI 组件包

1.1 分 lite 和全量两个版本。全量 = lite 的全部文件 + AI 组件包（本地 AI 运行库、OCR 依赖和模型）。包根目录有 `ai-pack.json` 就是全量版；它列出组件包的文件和哈希，`fusion-manifest.json` 只列本体文件，并用 `aiPack` 写明这个版本需要的组件包版本。

**发布资产**（每个 Release 都带）：

- `Loadout-<版本>-lite-portable-windows-x64.zip`：本体。更新器只下载这个。
- `Loadout-<版本>-portable-windows-x64.zip`：全量（本体 + 组件包），给第一次下载的人。沿用 1.0 的名字，所以 1.0 的更新器下载的就是它。1.0 的更新器拒绝清单之外的任何文件，因此这个 ZIP 里的 `fusion-manifest.json` 是完整清单：本体、组件包和 `ai-pack.json` 都列出（`archive.py` 打包时生成）。lite 和组件包的清单不变。1.1 只按 `ai-pack.json` 认组件包，更新器也只下载 lite，所以两种清单都能用。
- `Loadout-ai-<组件包版本>-windows-x64.zip`：组件包单独一份。

每个都配同名 `.sha256`。

**更新**：下载并校验本体后，如果当前安装有组件包：版本和新本体要求的一样，就从当前文件夹逐个复制并校验；不一样就从同一个 Release 下载组件包资产。没有组件包的安装（lite）更新后仍是 lite。换文件夹、失败回滚的流程不变，组件包跟着新文件夹一起换、一起回滚。

**补装组件包**：lite 用户在“功能”页点安装，更新器从当前版本的 Release 下载组件包，校验后把文件放进程序文件夹，最后写 `ai-pack.json`。组件包的文件和本体不重叠，正在运行的文件不会被替换，不需要重启。失败时只删除这次复制进去的文件。

**信任边界不变**：同样只连 GitHub、同样的 SHA-256 校验和路径检查；组件包按 `ai-pack.json` 逐个文件核对，多出的文件拒绝。运行时永远不从 Hugging Face 等模型网站下载：transformers.js 只读 `ai/models`，构建时按 `development/fusion/ai-models.json` 固定的版本和哈希取模型。

**为什么不是两套独立的包**：组件包约 200 MB、很少变。分开后全量用户每次更新只下载本体，组件包版本变了才重新下载。
